# 2026-07-30 — Named HTTPS for local services: `*.internal` via dnsmasq + Caddy

Nine local services had accumulated behind memorised `127.0.0.1:<port>` pairs —
the AI stack (CLIProxyAPI, CPA-Manager-Plus, Ollama, oMLX, LM Studio, gbrain)
and the observability stack (Grafana, Prometheus, Alloy). They now answer on
`https://<name>.internal` with no port and a trusted certificate.

## What was chosen, and what was ruled out on evidence

Four approaches were tested before settling. Recording the negatives because
each looked correct on paper.

- **`.local` names.** macOS reserves `.local` for mDNS (RFC 6762) and routes
  every `.local` lookup to mDNSResponder, never consulting `/etc/resolver` or a
  local DNS daemon. Verified: `nexus.local` resolves (Bonjour publishes the
  machine's own name, LocalHostName `Nexus`) while `cliproxy.local` and
  `grafana.local` return nothing. A unicast resolver cannot serve this suffix,
  which is why the Pi-hole analogy misleads — Pi-hole is dnsmasq, and macOS
  bypasses it for `.local` specifically.
- **Publishing into mDNS ourselves** (`dns-sd -P cliproxy _http._tcp local 8317
  cliproxy.local 127.0.0.1`). This *works* — the name resolved immediately. But
  `dns-sd -P` has no interface scoping, so the registration is advertised on
  whatever LAN the machine is joined to, and it also registers a browsable
  Bonjour service. Gating on network identity (gateway MAC is readable without
  a Location Services grant; SSID is not) would keep names private but also
  make them stop resolving away from home, which defeats the purpose.
- **Tailscale Services.** Technically the strongest option: real Let's Encrypt
  certificates, each service on its own virtual IP so all sit on 443, reachable
  from other tailnet devices. Verified working at HTTP 200 with a 17 ms
  handshake. Ruled out on coupling, not capability: hosting a service requires
  an ACL-**tagged** node (`service hosts must be tagged nodes`), which means a
  policy edit and re-authenticating this machine into tailnet ownership;
  MagicDNS is fully dead under ProtonVPN (verified — even querying
  100.100.100.100 directly returns nothing, though tailnet *routing* survives),
  so it also needs ProtonVPN's Custom DNS pointed at MagicDNS, moving all DNS
  off Proton's resolver; and names vanish whenever Tailscale is down.
- **TLS directly on CLIProxyAPI.** Tried earlier and it broke every harness
  login with "Network connection failed", because the mkcert root CA had never
  been installed into the System keychain (`mkcert -install` needs an
  interactive sudo). The CA is trusted now, but terminating TLS once in a proxy
  beats configuring it per service, so `tls.enable` stays `false`.

A note on diagnosing the Tailscale timeout, since three plausible theories were
all wrong: ProtonVPN was disconnected, Little Snitch blocked nothing, and
certificates provisioned fine. The cause was that Funnel — deliberately serving
gbrain's HTTP endpoint on :8787 — makes the node's FQDN resolve to Tailscale's
**public ingress** (185.40.234.x), and Funnel serves only 443/8443/10000, so
:8317 hung. Forcing resolution to the tailnet IP returned 200 instantly. That
Funnel is load-bearing and was left alone.

## The stack

Three layers, all on loopback, so names work offline, under ProtonVPN, with
Tailscale off, and broadcast nothing.

- **dnsmasq** answers `*.internal` → 127.0.0.1 from a single wildcard line.
  It listens on **port 5354**, not 53: a high port needs no root, so it runs as
  an unprivileged user LaunchAgent and cannot contend with another resolver.
  `/etc/resolver/internal` (with a matching `port 5354`, a directive `man 5
  resolver` confirms) scopes macOS to send only this suffix there, leaving
  system DNS — and therefore ProtonVPN and Tailscale — untouched. This is the
  same per-domain mechanism Tailscale itself uses for split DNS, so the two
  coexist by design rather than by luck.
- **mkcert** issues one certificate carrying every site name as an explicit
  SAN. A `*.internal` wildcard does **not** work: validators reject wildcards
  directly under a top-level suffix (the rule that outlaws `*.com`), and curl
  failed with "no alternative certificate subject name matches" until the cert
  was reissued with explicit names. The configure script derives the SAN list
  from the Caddyfile's site blocks and reissues automatically whenever a name
  is missing. The root CA is already in the System keychain, so the names are
  trusted with no per-client work.
- **Caddy** terminates TLS on :443 and reverse-proxies by `Host:` header to
  each loopback port. It runs **unprivileged** (`brew services start caddy`):
  macOS lets a user process bind a low port on all interfaces (the wildcard),
  though never on a specific address — `127.0.0.1:443` returns permission
  denied, verified with a bare socket test. So Caddy takes the wildcard, which
  was only possible after gbrain's Tailscale Funnel moved off 443 (now
  `https://nexus.tail5e2005.ts.net:8443` → 127.0.0.1:8787; the funnel's local
  listener held `*:443`). Never `sudo brew services start caddy`: it chowns
  the Cellar paths root:admin and breaks later upgrades — observed, then
  reverted with a chown.

The wildcard bind faces the LAN, so close it deliberately: a Little Snitch
inbound deny rule for `caddy` (the `.internal` names themselves only ever
resolve to loopback).

Adding a service later is one block in `manifests/caddy/Caddyfile`. DNS covers
it via the wildcard; the configure script reissues the certificate on the next
run.

**The AI harnesses were deliberately not migrated.** Codex's `[profiles.sol]`
and the rune launch profiles still point at `http://127.0.0.1:8317`, so Claude
Code and Codex never depend on Caddy or dnsmasq being healthy. The names serve
browsing; machine-to-machine calls that already worked are left alone.

## Harnesses wired to the proxy globally

Separate from the naming work, and the reason it matters: CPA-Manager-Plus only
meters what passes through CLIProxyAPI, so a harness talking to its vendor
directly is invisible to it. Claude Code, Codex, and grok now default to
`http://127.0.0.1:8317` — loopback, not `cliproxy.internal`, so no harness
depends on Caddy or dnsmasq.

- **Claude Code** and **grok** via environment, from a new chezmoi file
  `dot_config/zsh/cliproxy.zsh` sourced by `dot_zshenv`. It reads only the
  `CLIPROXY_*` values out of `~/.env`; sourcing the whole file would export
  every unrelated secret into every shell.
- **Codex** via `model_provider` at the **top level** of `~/.codex/config.toml`,
  not in a profile. This is load-bearing: `rune run codex` — HarnessCouncil's
  path — rejects a profile's `--profile` argument and silently falls back to the
  vendor endpoint, unmetered. A profile-only provider looks correct and meters
  nothing. Codex authenticates with `CLIPROXY_API_KEY_CODEX` so spend splits by
  harness rather than pooling on the default key.

**Account routing had to change first.** `force-model-prefix` was `false`, so an
unprefixed model request load-balanced across *both* Claude accounts — blended
rate limits and corrupted per-account spend, exactly what a bare `claude`
command would have hit. It is now `true`, and `claude@martinzeman.net` carries
no prefix: unprefixed pins that account, `alt/` reaches the other, and
`rune launch alt@claude` still switches deliberately.

**Unwiring is one command,** and it has to cover two mechanisms because Codex
has no environment override — an env-only toggle would leave it pointed at a
dead proxy while the others recovered:

```
cliproxy off | on | status      # all three harnesses
noproxy <cmd>                   # one command against vendor endpoints
```

`cliproxy off` comments out the Codex line via a `CLIPROXY-TOGGLE` marker,
leaving `[profiles.sol]`'s own copy intact so `--profile sol` stays deliberate.
`[profiles.direct]` restores the vendor provider for one run. Both directions
were exercised, not just the happy path.

`scripts/verify/harness-proxy.sh` asserts each mechanism separately, plus the
attribution key and deterministic account routing, and skips cleanly when
`cliproxy off` is set.

**agy stays direct**, and the reason corrects an earlier claim of mine. A
`strings` scan found no base-URL variable, and that was reported as "no override
exists" — wrong. `agy` honours an undocumented `CLOUD_CODE_URL`, proven by
pointing it at a local listener and capturing its bootstrap
(`/v1internal:loadCodeAssist`, `:setUserSettings`, `:listExperiments`). The real
blocker is the proxy: it serves `/v1internal:*` only as an *upstream* target and
404s those routes inbound, which upstream's own gemini-cli plugin notes state
outright. Routing agy would need a proxy-side shim, and Google's terms treat
third-party access to those services as grounds for account termination. The
`CLIPROXY_API_KEY_GEMINI` key stays generated but spare.

An absence claim from a shallow binary scan is not evidence. Two comments that
implied agy support were corrected, including one in `cliproxyapi.conf` that a
later reader nearly took as upstream documentation.

## Verified end to end

All nine names resolve to 127.0.0.1 and serve trusted TLS with no `--cacert`:
eight backends answer (200/302/307/401/404 per service), `brain.internal`
correctly 502s while gbrain is down. The harness regression guard holds —
`rune launch main@claude --dry-run` still shows
`ANTHROPIC_BASE_URL=http://127.0.0.1:8317`. `/etc/resolver/internal` requires
`sudo mkdir -p /etc/resolver` first; macOS does not ship the directory (the
configure script does both).

The verify script also probes every non-loopback address this machine holds
(LAN, VM bridges, tailnet) with a spoofed Host header, since the `*:443` bind
is only closed by policy living outside this repo. All six refuse.

Two traps worth keeping:

- **`curl --connect-to` cannot be used for that probe.** It reported an
  unreachable connection even for a listener that was demonstrably reachable,
  which made the check silently unfailable — a test that always passes. Caught
  by running a control against a service known to be exposed. `--resolve` is
  correct and does distinguish the two cases.
- **The check asserts the property, not the mechanism.** macOS's own
  Application Firewall is also enabled here (`socketfilterfw` state 1), so a
  refusal cannot be attributed to the Little Snitch rule alone. That is fine —
  what matters is that the listener is unreachable — but do not read a passing
  check as proof the Little Snitch rule exists.

Only the incoming deny is wanted for Caddy. An accompanying "allow any outgoing
connection" rule is not: this configuration never egresses (backends are
loopback, ACME disabled, admin off), so leaving outgoing unruled means Little
Snitch will surface any future egress as a prompt instead of permitting it
silently.

## Fixed in passing: Homebrew could not install

`brew install` crashed at CLI-parse time. Root cause: brew's vendored bundle
held two json gems, `json-2.20.0` and `json-2.21.1`. `Gemfile.lock` pins
2.21.1, but its native extension never finished building — no
`gem.build_complete`, no compiled output, and a `gem_make.out` ending in
`make failed` / `Broken pipe` (an interrupted 2026-07-29 update). 2.21.1's
Ruby code loading against 2.20.0's older extension died on `undefined method
'default_sort_keys_proc='` before any command could run; only the shell
fast-paths (`--version`, `list`) survived.

Do **not** fix this by deleting `vendor/bundle` wholesale — tried, and it
removes brew's own runtime deps (bootsnap, sorbet-runtime), leaving brew unable
to boot far enough to reinstall them. The bundle files are git-tracked in
`/opt/homebrew`, so the working repair is restoring them through git and
letting brew reconcile from there.

## Containing the proxy's egress

The proxy holds every subscription credential and sees every prompt, so what
it can reach matters more than what it claims to do. Observed rather than
assumed, by watching real connections:

- CPA-Manager-Plus makes **no external connection at all** — every socket is
  loopback, including its own reads of the proxy through Caddy. It is denied
  all egress on that basis.
- CLIProxyAPI serves requests over exactly one external connection, to
  `api.anthropic.com`, as it should. But on **every startup** it also contacts
  `github.com` and a GitHub Pages address (management-panel assets) and
  `antigravity-hub-auto-updater-…us-central1.run.app`. None are model APIs.
  The binary further embeds public-IP lookup services (`api.ipify.org`,
  `ifconfig.me`, `ipinfo.io`) and maintainer-operated hosts
  (`cpamc.router-for.me`, `models.router-for.me`) that were not observed in
  use.

`manifests/littlesnitch/ai-proxy-containment.lsrules` is therefore an
allowlist: model vendors, plus the panel and Antigravity updater as named
exceptions, then a catch-all deny — which covers the IP-lookup and
maintainer hosts without naming them. Both exceptions are deliberate choices,
not oversights: the panel is allowed to keep tracking upstream, at the price
of being the one path by which remote code reaches the page holding the
management key. The Antigravity host is named in full rather than allowing
`run.app`, which would open every Cloud Run service anyone operates.

Process paths are durable here, which PROV-0013 warns is usually not true of
Homebrew binaries: the kernel records the exec path, and `brew services`
execs `/opt/homebrew/opt/cliproxyapi/bin/cliproxyapi`, so the rule survives
upgrades without naming a Cellar version.

The plugin loader is off (`plugins.enabled: false`, enforced by
`scripts/configure/cliproxyapi-usage.sh`). Plugins load as native code inside
the process holding the credentials and are fetched from remote registries;
none are installed, so this costs nothing.

`scripts/verify/ai-proxy-egress.sh` checks the effect rather than the rules,
since Little Snitch state cannot be read back: it resolves every established
connection of both processes and reports anything outside the allowlist. It
earned its keep immediately by catching all three startup callouts on the
first run.

What this does **not** solve: a compromised proxy could embed stolen data in
a legitimate request to a vendor it is allowed to reach. An egress allowlist
constrains side channels, not the vendor channel, so it complements binary
provenance rather than replacing it.

### Source audit of CLIProxyAPI

A read of the source at v7.2.111 found **no backdoor, no covert telemetry, and
no outbound POST to any non-provider host**. The three maintainer-adjacent
calls are download-only GETs: a model catalog (`models.router-for.me`, with
`raw.githubusercontent.com` tried first and an embedded catalog as final
fallback), the panel assets, and the Antigravity version manifest. The
IP-lookup services fire only during interactive OAuth login, to print SSH
tunnel instructions, never at startup. Blocking all of them degrades nothing
at inference time.

Three findings do matter:

- **CVE-2026-8081 is unpatched at HEAD.** A management endpoint substitutes a
  `$TOKEN$` placeholder in a caller-supplied header with the live stored OAuth
  token and sends it to a caller-supplied URL, with no loopback or RFC1918
  filtering. It is a documented feature, not an accident. It is unreachable
  while the management API is off, but this machine needs it on: CPA-Manager-
  Plus drains the usage queue through `/v0/management`. Management handlers
  also set `Access-Control-Allow-Origin: *`, so a web page visited while the
  proxy runs can reach the endpoint if it holds the key. **The egress
  allowlist is what contains this**: the token can only be mailed to a host
  the proxy is permitted to reach, and the catch-all deny covers the rest.
  That interaction is the main reason the allowlist is worth keeping.
- **Panel and plugin integrity is transport-only.** Both verify a digest that
  is published by the same GitHub release that serves the artifact, so
  whoever controls a release controls both. There is no independent
  signature. The panel's fallback source (`cpamc.router-for.me`) is written
  with **no verification at all**; the catch-all deny blocks it. Plugins are
  `dlopen`ed in-process with full access to every token in memory, which is
  why the loader is off here.
- **Nothing gets fixed upstream.** Fifteen security reports were closed
  `not_planned` with zero comments and no maintainer reply, and the CVE
  reporter documented no vendor response. There is no channel through which a
  future finding gets addressed. That predicts the next incident better than
  any single bug, and it is the strongest argument for keeping this stack
  contained by configuration we control rather than by trust.

Separately, exposed instances of this software are actively hunted: a
published study ran weak-password CLIProxyAPI honeypots and recorded
credentials harvested at scale. This machine binds loopback and denies the LAN
face, which is the property that matters there.

### Source audit of CPA-Manager-Plus

Clean, and stronger than its neighbour on every axis checked. No CVEs, no
advisories, no telemetry, no phone-home, and no allegations in the tracker in
either English or Chinese. Source is fully published and built by a pinned
CI pipeline rather than shipped as an opaque binary, and the maintainer
account is long-lived with a real second contributor.

Two things it does that the runtime observation could not show:

- Vendor hostnames in the binary are a false positive. They are built as
  *payload* and posted to the gateway's own management API, so the dashboard
  never opens a socket to a model vendor. Its only genuine third-party calls
  are three model-price catalogs, fetched solely when price sync is clicked;
  the release-version card runs in the browser, not the daemon. Denying the
  process all egress therefore costs only that optional sync, which fails
  visibly.
- The management key is encrypted at rest with AES-256-GCM under a `0600`
  key file, and admin auth is PBKDF2 with a constant-time compare. That
  protects a stolen database file, not an attacker who already has the
  filesystem.

Its two recommendations were already in place before the audit landed: bind
to `127.0.0.1:18317`, and verify the release checksum on install — upstream's
own installer downloads without checking the `checksums.txt` it publishes,
while `scripts/install/cpa-manager-plus.sh` refuses to install on mismatch.

The residual risk is structural rather than evidential, and worth stating
plainly: unsigned artifacts, no provenance attestation, and commit
concentration in two people mean a compromised maintainer account could ship
a malicious release with nothing in the pipeline to flag it. That is an
argument for reading upgrade diffs, not for avoidance. It applies to the
proxy too, which additionally has no working channel for security reports.

## Aliases and upstream tracking

`cpamc.internal` and `cpamp.internal` join the Caddy site blocks for
`cliproxy.internal` and `usage.internal`, each name matching the product it
refers to: CPAMC is the Cli-Proxy-API Management Center that the proxy serves
on 8317, CPAMP is CPA-Manager-Plus on 18317. They are additional addresses on
the existing blocks rather than new ones, so the panel redirect and proxy
targets are shared by construction, and the certificate picked both up from
the site-address parsing.

CLIProxyAPI is upgraded through Homebrew, which owns the binary; the
management panel's version banner reports GitHub releases and so runs a patch
ahead of the formula (7.2.111 upstream against 7.2.110 stable at the time of
writing). Take upgrades from `brew upgrade cliproxyapi`, not from the panel,
or the installed binary drifts from what the Brewfile describes. The upgrade
leaves `$(brew --prefix)/etc/cliproxyapi.conf` untouched — verified
byte-identical across 7.2.100 → 7.2.110 — so the managed settings survive.

CPA-Manager-Plus now tracks upstream instead of a pinned release: the
installer resolves the latest tag and compares it against a `.version` stamp
beside the binary. The stamp exists because the binary has no version flag —
invoking it bare starts a server and writes to the data directory rather than
printing anything. Upgrading replaces the binary in place, so the installer
stops the service first and restarts it afterwards. Upgraded to v1.11.10 with
the spend history and the seeded admin credential intact; a rerun reports the
version current and does nothing.

## Subscription failover: fill-first + persisted cooldowns

Verified against CLIProxyAPI source (v7.2.111) how multi-account failover
actually behaves, then configured for it:

- On a Codex `usage_limit_reached` 429 the proxy parses OpenAI's own
  `resets_at` from the error body, cools that credential until the real
  window reset, and continues the same in-flight request on the next
  credential — the client never sees the error unless every credential is
  exhausted. Transient rate limits get a short exponential backoff instead
  (1s doubling, 30 min cap), absorbed by the outer retry loop when the wait
  fits inside `max-retry-interval`.
- `routing.strategy: "fill-first"` picks the first available credential in
  deterministic order, so a second subscription is a spillover, not a
  load-balance peer.
- `save-cooldown-status: true` persists quota windows as `.cds` files next to
  the auth files, so a proxy restart does not forget an exhausted account.
- The `quota-exceeded.switch-project` / `switch-preview-model` keys are
  config-only no-ops in this version (only `antigravity-credits` has a
  runtime consumer).

Ordering comes from `priority` in the auth JSON, and the grouping is safe for
failover: `availableAuthsForRouteModel`
(`sdk/cliproxy/auth/conductor_selection.go:271`) inserts only *non-blocked*
credentials into the priority map, then picks the highest priority group
present. A cooling account therefore drops out of the map entirely and the
next group serves; it wins again automatically once the cooldown expires.
Within a group, order is by auth ID (the auth file's path).

Claude gets the same treatment, which reverses this session's earlier
`force-model-prefix: true` decision. That flag was turned on to stop
round-robin blending the two Claude accounts mid-session, but it does so by
removing every prefixed credential from the bare model pool — which also
removes it from failover, so an exhausted primary dead-ended at 429 while the
alt subscription sat idle. Fill-first plus priority provides the determinism
instead, so the flag is off: `alt` now registers both `claude-*` and
`alt/claude-*` (confirmed in `/v1/models`), main carries `"priority": 1`, and
a bare request lands on main while `alt/<model>` still targets alt
explicitly. Verified end to end — a bare `claude-haiku` request through the
proxy was served by the main account and metered as such.

The one asymmetry: the Claude executor has no analog of
`parseCodexRetryAfter`. Its error path
(`internal/runtime/executor/claude_executor_execute.go:163`) builds a plain
status error and parses neither `retry-after` nor
`anthropic-ratelimit-*-reset`, so an exhausted Claude account cools on the
generic exponential backoff (1s doubling, 30 min cap) rather than until the
real window reset. Failover itself is unaffected; only return-to-primary is
probe-based, costing one failed request per probe and returning within about
half an hour of the true reset. A mid-stream error event is converted to 502
(`claude_executor_stream.go:299`) and treated as transient, so only pre-stream
429s mark quota at all.

`scripts/verify/harness-proxy.sh` asserts the invariants this rests on:
fill-first, `force-model-prefix` off, and exactly one Claude account at top
priority (more than one would round-robin within the winning group and blend
accounts again).

Adding a second Codex subscription later: `cliproxyapi --codex-login` (the
file watcher hot-loads the new `codex-<account>-<email>-<plan>.json`), then
add top-level `"priority": 1` to the preferred account's JSON and leave both
unprefixed. CPA-Manager-Plus attributes them separately by account either
way.

## Claude Code and the proxy are mutually exclusive

Routing Claude Code through the proxy costs every claude.ai-account feature:
Remote Control, `/schedule` routines, claude.ai MCP connectors, Artifacts,
Ultraplan and Ultrareview, and web/mobile access. Two independent gates cause
it. `ANTHROPIC_AUTH_TOKEN` being set disables connectors and routines even
alongside a valid claude.ai login, and since Claude Code v2.1.196 Remote
Control is disabled whenever `ANTHROPIC_BASE_URL` names a host other than
`api.anthropic.com`, "even if you sign in with claude.ai". The endpoint check
is a condition of its own, with no admin override and no environment escape,
so no configuration keeps Remote Control and a local gateway at once.

Paths that look like workarounds and are not: `claude setup-token` /
`CLAUDE_CODE_OAUTH_TOKEN` is documented as model-requests-only and is refused
by Remote Control; Bedrock and Vertex lose exactly the same features while
billing per token; and the one documented subscription-preserving mode
(setting only `ANTHROPIC_BASE_URL`, no gateway credential, so the claude.ai
login stays the active credential) needs a passthrough gateway. CLIProxyAPI
substitutes credentials by design and answers 401 to any request without its
own key, verified directly, so that mode cannot apply here — and it excludes
Remote Control regardless.

The design that follows: Codex and grok stay proxied permanently, having no
claude.ai features to lose, while **Claude Code defaults to direct** and
proxied Claude becomes a per-session choice through the rune launch profiles.
The global `ANTHROPIC_*` export in `~/.config/zsh/cliproxy.zsh` currently
inverts this, so every terminal-launched session silently forfeits those
features; the GUI-launch gap noted below is what has been preserving them.

This also matches the terms. Anthropic's legal and compliance page prohibits
third parties routing requests through Pro/Max credentials, which is what
gateway routing of both subscriptions is; owning two subscriptions and
signing into each with the official client is unaddressed by contrast.

One diagnostic lesson worth keeping: "You've hit your monthly spend limit,
run /usage-credits" is a known mislabel (claude-code#67579) and does not
imply a spend cap. The proxy's own cooldown records are a better source —
they showed a single model cooling on one account with an explicit reset
time, while other models kept working. Check `/usage` before buying credits.

## Follow-ups
- **Long-running and GUI-launched sessions escape the proxy silently.** The
  session that did this work carried no `ANTHROPIC_BASE_URL` (checked in its
  process environment) and produced no `claude-fable-5` rows in CPAMP, so it
  and its subagents billed the vendor account directly — one subagent died on
  an Anthropic spend limit that would have spilled to the alt subscription had
  it been routed. The wiring only reaches processes started from a login shell
  after it was installed: `~/.zshenv` is not sourced by Dock or Spotlight
  launches, and an already-running session never picks it up. `cliproxy
  status` reports the shell's state, not the state of harnesses already
  running, so nothing surfaces the gap. Restarting from a terminal fixes the
  individual case. The durable fix for GUI launches is `launchctl setenv`,
  which has a real cost: it places the proxy token in the environment of every
  GUI application on the machine, not just the harnesses. Worth deciding
  deliberately rather than by default.
- **Grafana absolute links.** `root_url` still says `localhost:3000`, so some
  generated redirects bounce back to the port. Fix is `GF_SERVER_ROOT_URL` in
  the config `scripts/configure/observability.sh` manages. Prometheus may want
  `--web.external-url` for the same reason.
- Any `.internal` search domain pushed by a future VPN profile could interact
  with this suffix. Nothing observed today.
