# 2026-06-11 claude-box behind the VM wall; Zed config ownership

## What changed

The Linux-isolation tier ([VIRT-0002][V2]) gained its operational layer, and it
is deliberately not a tool: build-arg-templated Containerfiles as definitions,
plus the [SandboxToolkit][SKILL] skill carrying every invocation. No wrapper
scripts, no new binaries. A `forge sandbox` Rust subcommand was designed and
consciously shelved; the skill exercises the same workflows and can be promoted
later if profiles outgrow it.

- **SandboxToolkit skill** (`skills/SandboxToolkit/`): SKILL.md routes to two
  companions: `AppleContainer.md` (service lifecycle, preflight, the gotcha
  catalog) and `ClaudeBox.md` (image template, auth, run modes).
- **claude-box image** (`scripts/sandbox/claude-box/Containerfile`):
  ARG-parameterized (BASE_IMAGE, APT_PACKAGES), non-root, node + git +
  Claude Code. Variants are build args, not new files.
- **Scope correction that shaped the design**: the box is not only for
  autonomous runs. The entire harness runs behind the VM wall as a security
  layer: interactive sessions, persistent settings and history in a named
  volume, and autonomous `--dangerously-skip-permissions` runs as one mode
  among three.
- `scripts/sandbox/experiment.sh` retired: it reproduced two documented
  gotchas (no `-m 4g`, sandboxed-when-wrapped) and contradicted the
  definitions-plus-skills direction.
- VIRT-0002 amended: container CLI is 1.0.0 (Homebrew upgraded it), skill
  replaces the script reference, full-harness scope recorded.

## Research that closed doors

vibekit, appealing in its README, failed a source-level audit of the shipped
npm package: no Apple container support (Docker/podman CLIs only, demoting
runs to the shared-kernel tier), sandboxing off by default with silent
fallback to unsandboxed host execution, the advertised redaction layer absent
from the published bundle, dormant maintenance, and unreleased code that
rewrites `.claude/settings.json`. Rejected outright.

icazemier/claude-apple-container (the only prior art on this exact stack) was
mined rather than adopted: an interactive dev-box of ~1,400 bash lines with no
autonomous support, but its encoded gotchas were transplanted into
`AppleContainer.md`: exit-0 on gRPC transport errors, post-sleep transport
staleness, orphaned `container-runtime-linux` VMs, the 1 GiB default that
OOM-kills Claude Code, builder-VM OOM, virtio-fs vs node_modules.

First-party facts that anchored the design: Anthropic blesses
skip-permissions only inside a container, VM, or sandbox runtime; the CLI
rejects the flag as root (hence `USER node`); `claude setup-token` plus
`CLAUDE_CODE_OAUTH_TOKEN` is the documented headless auth; no official
runnable image exists, so the micro-Containerfile is unavoidable and
sufficient.

## Zed config ownership: chezmoi live, forge-provision baseline

Zed's config got a two-lane ownership model after the first round of GUI
tweaks landed:

- **chezmoi owns the live config.** `dot_config/zed/` (settings.json,
  keymap.json) joined the dotfiles repo next to ghostty, gitui, and tuicr.
  Capture after GUI tweaks is one command: `chezmoi re-add`.
- **forge-provision keeps the baseline.** `manifests/zed/` stays as the
  first-provision seed; most of it is unopinionated best practice (vim trio,
  telemetry off, declarative extensions, agent wiring), with personal taste
  limited to the theme. `scripts/configure/zed.sh` is now seed-only: it
  copies the manifest into `~/.config/zed/` only when no file exists there,
  never overwrites, so the two lanes cannot fight over the same file.

The captured GUI round-trip that prompted this: theme dark to Ayu Dark
(dark without purple tones; the published Catppuccin extension ships only
the mauve-accent build), relative line numbers `wrapped`, autosave on focus
change, project panel docked left (default is right), terminal
copy-on-select, Zeta data collection declined, worktrees trusted. Zed's GUI
writes preserved the JSONC comments and 4-space indent, so the round-trip
is lossless.

Fresh-machine order: `brew bundle` installs the cask, `chezmoi apply` lays
down the live config, `zed.sh` seeds from the manifest only if chezmoi has
not run yet. Either order converges; whichever lane writes first wins.

## Apple container service forensics

The first claude-box build surfaced a failure chain worth its own record,
now encoded in the SandboxToolkit gotcha table and
`scripts/install/container.sh`:

- **Symptom**: every `container` CLI command hung forever with zero output,
  surviving even a pkg reinstall. The daemon was never wedged: the client
  performs a launchd Mach-service lookup that blocks indefinitely when the
  apiserver is unregistered or crash-looping.
- **Root cause (Homebrew)**: `container system start` derives
  `CONTAINER_INSTALL_ROOT` from the invoking binary's path. Invoked via the
  linked `/opt/homebrew/bin/container` it wrote `INSTALL_ROOT=/opt/homebrew`,
  where Homebrew links no `libexec/`, so the apiserver exited 1 on
  `cannot find any plugins with type network` and launchd throttled the
  respawns. The keg path (`/opt/homebrew/opt/container/bin/container`)
  derives a root whose `libexec/` exists; the formula caveat encodes exactly
  this invocation.
- **Second failure (pkg detour)**: correct plist, but no launchd
  registration at all; one `launchctl bootstrap gui/501 <plist>` revived it.
  The decisive diagnostic was running `container-apiserver start` in the
  foreground: it came up cleanly, pinning the fault on registration rather
  than state.
- **Forward trap**: the plist stores the resolved Cellar path (`1.0.0_1`),
  so every `brew upgrade container` strands the service on a deleted keg
  until the keg-path `container system start` rewrites it.

Resolution: back on Homebrew, service healthy, claude-box built and
smoke-tested: Claude Code 2.1.173 inside its own VM, non-root, git present,
sub-second boot, `--rm` teardown.

## markdown-oxide config and the Zed-as-forge-target finding

Investigated using Zed more heavily as a forge target. Two findings settled the plan:

- **Skills loading.** Zed's first-party agent loads Agent Skills from
  `.agents/skills/<name>/SKILL.md`, but those apply only to Zed's own agent.
  The daily driver here is Claude Code via ACP, which loads its own
  `.claude/skills` independently, so a forge `.agents/skills` compiler target
  is low priority, not urgent. Rules would map to a single `AGENTS.md`.
- **Markdown / Obsidian.** markdown-oxide (already in auto_install_extensions,
  extension confirmed installed) is the PKM layer. It auto-imports daily-note
  folder, new-file location, and date format from the Atlas vault's Obsidian
  config, and its useful behaviors are default-on (`![[embed]]` transclusion as
  inlay hints, unresolved-wikilink diagnostics, backlinks-on-hover). Math and
  reliable inline images are GPUI core limits no extension can fix; Obsidian
  stays the render-heavy lane.

Config is therefore deliberately minimal: a global
`~/.config/moxide/settings.toml` (oxide reads its own file, not Zed's
settings.json) that pins only the daily-note date format and documents the
import behavior, while extending wikilink completion and backlinks to forge's
own ADR/journal/skill markdown. Seeded by `scripts/configure/markdown-oxide.sh`
(seed-only, same chezmoi-owns-live model as Zed), captured into chezmoi
`dot_config/moxide/`.

The forge-cli dashboard (its own `dashboard` branch: axum + htmx + Askama,
renders markdown via marked.js but does not resolve wikilinks) is the better
integration target via a future vendor-neutral context/MCP server over its
`commands::view` model, not a Zed-specific extension. Backlogged, not built.
