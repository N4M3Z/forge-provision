# 2026-06-04 — Sandboxing stack: Seatbelt harness, Apple container, tier model

## What changed

The machine now has a layered isolation stack instead of a single permission
layer. Three ADRs record it: [ARCH-0031][31] (the platform-neutral tier model:
process sandbox < container < VM, each workload at the weakest sufficient
tier), [VIRT-0001][V1] (Claude Code's built-in Seatbelt sandbox, enabled
globally in auto-allow), and [VIRT-0002][V2] (Apple container as the
VM-backed Linux tier, OrbStack bounded to a Docker-API convenience role).

Concretely:

- **Claude Code Seatbelt sandbox** enabled in user settings: credential
  `denyRead` (Trail of Bits baseline), hostname allowlist for GitHub, npm,
  crates.io, Homebrew, subprocess env scrub, and exclusions for the VM and
  Go-TLS tools (`docker`, `gh`, `brew`, `container`, `prlctl`, `orb`).
  Verified empirically: out-of-cwd writes die with kernel EPERM, cwd writes
  pass, no credential env reaches subprocesses.
- **Apple container** installed (`brew "container"` plus
  `scripts/install/container.sh` for the non-interactive bootstrap) and
  smoke-tested: alpine pulled, ran in its own VM, auto-removed.
- **OrbStack** installed as the Docker-API convenience layer; Docker enabled,
  Kubernetes and Linux machines off until needed.
- **Experiment harness** `scripts/sandbox/experiment.sh`: one-shot per-VM
  container mounting a single directory at `/work`, `--rm` teardown, optional
  `--locked` (read-only rootfs + tmpfs). Tested end-to-end: mount visible,
  zero host env leaked, container gone after exit.

## Lessons that cost time

- **Sandbox exclusions match the top-level command string only.** Running
  `bash scripts/install/container.sh` sandboxed the whole script, so the
  `brew install` inside failed on `/opt/homebrew` writes and misreported as
  an ownership problem. The same script's commands run directly (`brew
  install container`) matched their exclusions and worked. Provisioning
  scripts that wrap excluded tools must run outside the harness sandbox.
- **`prlctl` breaks under Seatbelt** (its helper call to `/bin/ps` gets
  EPERM), which is how VM managers earned their exclusion entries.
- **Apple container's first start prompts interactively** for a kernel
  download; `container system start --enable-kernel-install` is the
  scriptable form, now baked into the install script.
- **Apple container 0.12.3 has no per-run network-off switch**; isolation
  rests on the per-VM boundary, the single mount, and no env inheritance.

## Decisions and rationale pointers

"Is Docker the right sandbox?" turned out to be the wrong question; the
answer is a tier per workload. Docker/Colima/OrbStack all share one kernel
inside one VM and none can hold a macOS app; Apple container gives a VM per
container with no Docker engine; Parallels ([ARCH-0016][16]) remains the
macOS-app tier. Strict sandbox mode (`allowUnsandboxedCommands: false`) is
deliberately deferred until the exclusion list survives a week of real use.
